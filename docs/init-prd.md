一套自定义可交互的爬虫项目. 

这个文档是初始的混乱想法的记录, 更完整的架构决策参考[m1-architecture.md](m1-architecture.md)

# 预爬取
首先可以有一个预爬取过程，拿到一个网站的入口地址之后：
1. 先得到 Sitemap 文件，获取一些初始链接
2. 拿到这些链接的基础信息（Meta、Title 等）
3. 不做递归爬取，最终得到一个初始列表

# 分类打标能力
有一个大模型网页分类打标的工具能力：
1. 输入一个网站的基础信息（如 Meta Title 等），或者是网站的整体内容。
2. 交给这个分类打标工具进行处理。同一个页面打标支持多个标签结果.
3. 得出一个对页面的分类结果，比如博客页、详情页、QA 页、A产品/B产品、美国站点/欧洲站点/中国站点.
这些页面标签是由用户自定义的。

# 爬取配置
所以第一轮先预爬取，再分类打标，然后把结果反馈给用户。通过与用户交互，得到一个完整的爬取配置。
这个配置包括：
1. 基于链接url的规则/正则的黑名单和白名单
2. 基于打标结果的规则的黑名单和白名单

基于打标的网页爬取方式，是一个配置信息，用来决定是：爬取 Markdown 文件/爬取截图/爬取完整网页等

# 定制化爬取
接下来开始正式的爬取，这就是传统爬虫的流程了。需要维护：队列状态/并发处理/单个页面的爬取等等, 这是 Crawlee 框架很擅长的东西。但是要对执行过程中的一些点，通过一些方式进行自定义扩展。比如：

一. 链接处理
所有遇到的链接我都想存下来，但是通过上述两个类型的规则来判断，存在三种情况：
1. 白名单：是一定要爬取的
2. 黑名单：是一定不爬取的
3. 待定的：这些信息即使不爬取，我也想把链接保存维护着

二. 单页面爬取
对于命中白名单、需要爬取的页面，处理流程如下：

1. 首先用最基本的爬虫类型，得到网页的基础信息（Meta、Title 等），如果有正文内容当然更好。 然后拿这些信息走一下分类打标的流程。得到一些打标的结果
2. 基于打标的结果和前文的配置，然后再触发更多类型的页面数据爬取，比如说：截图/完整网页存档等

三. 数据存储和断点继续的能力
整体以文件形式维护, 设计的时候，考虑迁移。
整个上文的各类配置信息、爬到的链接列表和爬到的网页数据，我希望都能妥善存储，并且支持断点。
关于配置的存储方式，我希望以一个容易迁移的形式保存, JSON 其实挺好，还可读，但我担心 JSON 在修改用户上不太好用, 所以也可以用一个本地 SQLite 文件数据库来存储.
至于网页爬下来的数据就是在文件目录里存储.

关于断点功能，除了传统的断点续传以外，我还需要一种能力：
1. 每次启动可以先设定一个爬取量，比如说先爬 100 个(这100个是指在白名单里面的，爬取成功的)然后就停止.
2. 每轮爬取完成后，针对那些"待定"的链接，用户可以基于这些链接再进行一轮配置变更，决定如何处理，然后重新启动新一轮的爬取。
3. 在启动的时候还可以设定，对于已经爬完了、有数据的链接是怎样处理，是跳过还是更新？用户也可以启动"更新"爬取, 比如说设定：如果上次爬取时间已经超过一周，就爬取最新的内容。

# 管理单元
整个功能的主要管理单元叫做“站点”。
在站点之上，还有一个“项目”的概念，即一个项目下可以包含好几个站点。这主要起到了管理和区分目录的作用。
这也考虑到上述配置文件的可迁移性。应该保证能够很容易地在我创建一个新站点的时候，导入旧站点已有的配置。

这篇文档提到的迁移, 是指从一个项目/站点, 迁移到其他项目/站点, 从本地运行的状态, 迁移到apify托管状态, 可以无缝继续使用.

# 网页
上述所有能力最基本的是通过 CLI 来暴露，但也要做一个网页。

这个网页是一个独立的模块，是可选的。打开网页可以展示：
1. 上述的各个配置, 结果查看, 各种格式的结果预览等功能
2. 用户大概的完整操作流程是：
   1. 项目创建
   2. 站点配置/导入配置
   3. 初始inventory预爬取, 结果校验和配置修正
   4. 根据参数启动一轮爬取，查看本轮的结果
   5. 查看整个站点的完整运行情况，查看待定链接的情况。
